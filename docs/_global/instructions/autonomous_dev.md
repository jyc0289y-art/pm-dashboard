# 자율개발모드 (Autonomous Development Mode)

사용자가 "자율개발모드", "자율개발", "묻지말고 진행", "autonomous dev" 등을 요청하면 이 모드를 활성화한다.

## 핵심 원칙

1. **질문하지 않고 진행**: 사용자에게 확인/허가를 구하지 않고, 스스로 판단하여 최선의 구현을 선택
2. **할 일을 스스로 찾아서 진행**: 명시적 지시가 없어도 프로젝트 개선점을 탐색하고 구현
3. **주기적 커밋 & 푸시**: 의미 있는 단위로 git commit + push하여 모바일에서 확인 가능하게
4. **프로젝트 폴더 외부 수정 금지**: 작업 대상 프로젝트 디렉토리 외의 파일은 수정하지 않음

## ★ 전문가 패널 검토 루프 (2026-07-19, P50 오너 지시로 격상 — 자율개발모드의 표준 형태)

> 오너 원문: "나의 판단을 받지 않고 다음의 개발팀과 전문가집단이 각 턴이 완료되면 다시 검토해서 앱 출시가 가능하다는 판단이 들 때까지 나의 의견을 얻지말고 전문가 집단에 의해 개발을 완료시켜줘. … 꼭 이 앱개발 뿐만 아니라 기구설계, 문서작업 등 어떤 프로젝트나 작업을 진행하더라도 이 자율개발모드를 발동시키면 바로 적용되도록."

**적용 범위**: 앱 개발·기구 설계·문서 작업 등 모든 프로젝트/작업. "자율개발모드" 발동 즉시 아래 루프가 기본 동작이 된다.

### 발동 시 4단계 루프

1. **분과 구성 (최초 1회)**: 해당 도메인의 가장 표준적·선진적인 팀 구조로 분과를 편성하고, 분과별로 세계 최고 수준 전문가 페르소나를 필요한 만큼 초청한다 (`panel_discussion.md` 표준 준용, Workflow 멀티에이전트로 구현). 분과 명부는 프로젝트 기록물 + 누적 보고서 divisions 탭에 등재.
2. **벤치마킹 (최초 1회 + 필요시 갱신)**: 같은 분야에서 가장 성공적인 산출물 다수를 선정해 성공요인을 분해·분석하고(웹 리서치 포함), 우리 산출물에 적용할 결의(R-원장)로 변환한다.
3. **턴 반복**: [구현 → 자가 검증(테스트·캡처·G1~G5 게이트) → **분과별 패널토론 검토**(각 분과가 델타를 심사, 결함·개선 결의) → 기록(회의록·TRAP·보고서·검수페이지 누적) → 다음 턴 백로그 확정] 을 반복한다. 오너 의견을 기다리지 않는다.
4. **종료 판정**: 전 분과가 "완료/출시 가능" 판정(치명·중대 결함 0, 각 분과 릴리즈 게이트 통과)을 내릴 때까지 반복. 판정 도달 시 최종 보고서 + 출시 준비물 일체를 정리해 오너에게 결과만 보고한다.

### 오너 개입 규칙

- 오너 회신을 **기다리지도, 요청하지도 않는다**. 단 검수 페이지·누적 보고서는 매 턴 계속 발행(열람용·"회신 불요" 명기) — 오너가 언제든 개입하면 그 피드백이 최우선 백로그가 된다.
- **예외 (여전히 오너 확인 필수)**: 비가역·대외적 행위(실제 스토어 제출, 결제/과금, 외부 배포·공개, 법적 리스크), 프로젝트 정체성 변경(브랜드·타깃 전환), 예산 지출. 이 경우 해당 항목만 보류하고 나머지는 계속 진행.
- 패널 판정은 오너 취향의 **대리 판단**일 뿐이다 — 오너가 준 과거 피드백(피드백 이력 대장)을 각 분과 심사 기준에 반드시 포함시켜 취향 드리프트를 막는다.

### 세션 연속성

- 턴 사이는 ScheduleWakeup/loop로 자동 재개(같은 세션), 세션 종료 시에는 registry·세션지침에 "자율개발모드 진행 중 + 다음 턴 백로그"를 남겨 다음 세션이 이어받는다.
- 매 턴 종료 시 기록물 5종 갱신 + 로컬 커밋(푸시는 원격 존재+오너 기승인 시).

## 병렬모드 (Parallel Mode)

사용자가 "자율개발병렬모드", "병렬로 진행", "parallel autonomous" 등을 요청하면 활성화.

### 병렬 작업 흐름
1. **작업 분할**: 독립적으로 수행 가능한 작업들을 식별
2. **에이전트 분배**: 각 작업을 별도 Agent로 할당 (최대 7개 동시)
3. **호이스팅 방지**: 모든 에이전트에게 arrow function / setTimeout 패턴 사용 지시
4. **중간 검증**: 에이전트 완료 시마다 console error 확인 → 즉시 수정
5. **일괄 커밋**: 모든 에이전트 완료 후 빌드 검증 → 커밋 & 푸시
6. **반복**: 다음 라운드 에이전트 실행

### 에이전트 지시 템플릿
각 에이전트에 반드시 포함할 내용:
- "Read each file BEFORE editing"
- "Use arrow functions `() => myFunc()` for ALL event listener bindings to avoid hoisting issues"
- "Keep existing features working"
- "After editing, run `npx vite build` to verify no build errors"
- "Do NOT commit or push"

### 충돌 방지
- 에이전트 간 파일 수정 충돌 최소화: 가능하면 각 에이전트가 담당 모듈만 수정
- index.html은 여러 에이전트가 수정할 수 있으므로, 완료 후 충돌 해결 필요
- 에이전트 완료 후 빌드 실패 시 호이스팅 에러가 가장 흔한 원인 → typeof 체크 또는 setTimeout 패턴으로 해결

## 작업 우선순위

1. 사용자가 명시적으로 요청한 기능/수정 (최우선)
2. 기존 코드의 버그 수정
3. 미구현 기능 완성
4. 새로운 기능 추가
5. UX/UI 개선
6. 성능 최적화

## 작업 흐름 (단일 모드)

1. **탐색**: 코드베이스를 분석하여 미구현·버그·개선점 발견
2. **구현**: 묻지 않고 바로 구현
3. **검증**: preview 도구로 동작 확인 (빌드 에러, 런타임 에러 체크)
4. **커밋**: 의미 있는 단위로 커밋 메시지 작성 후 commit + push
5. **보고**: 완료된 작업을 간결하게 사용자에게 보고
6. **반복**: 다음 작업으로 이동

## 주의사항

- 기존 기능이 동작하는 코드를 깨뜨리지 않도록 주의
- 대규모 아키텍처 변경은 사용자 확인 후 진행 (이것만 예외)
- 커밋 메시지는 영어로, 변경 내용을 명확하게 기술
- 빌드 실패 시 즉시 수정 후 재커밋
