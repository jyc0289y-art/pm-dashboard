## 1. 온톨로지 — 무엇이고 무엇이 **아닌가**

### 1-1. ★ 가장 중요한 한 문장

> **온톨로지는 「무엇을 볼지」 정하는 장치이지, 「무엇이 중요한지」 알아내는 장치가 아니다.**

온톨로지가 하는 일은 *"무엇이 존재하고 무엇이 무엇과 어떻게 이어지는가"에 대한 약속(commitment)을
명시하는 것*이다. **가설공간을 표현·감사 가능하게 만드는 것**이지, 그 공간을 **탐색해 유의미한 것을
골라내는 것이 아니다.**

신호 선별을 실제로 하는 장치는 따로 있다 — 정규화, 교차검증, **계층적 축소추정(partial pooling)**,
캘리브레이션, 잔차 검정.

**⚠️ 오히려 위험**: 온톨로지는 관계 수를 폭발시켜 파생피처를 수백 개로 늘리고,
**규율 없이 쓰면 다중검정·과적합의 자동화 장치**가 된다.

### 1-2. 팔란티어 용어의 환원 (Pigsty 창업자 Ruohang Feng)

| 팔란티어 | 실제 |
|---|---|
| Object Type | **Table** |
| Property | **Column** |
| Link Type | **Foreign Key** |
| Action Type | **Stored Procedure** |

> *"Every capability trumpeted in Palantir's Ontology documentation is natively supported by
> PostgreSQL. **License fee: zero.**"*

역사적 반복 — ER 모델링(1976) → OOP(1990s) → Semantic Web(2001) → Ontology(2020s).
독립 벤더 리뷰(Lokad, 4.7/10)도 **기술적 신규성의 증거는 제시하지 않는다**고 평가.

**다만 양쪽이 인정하는 것**: 스키마·권한·액션·SDK가 **하나의 런타임에서 강제(enforce)된다**는 점.
**새로운 것은 개념이 아니라 강제의 범위다.**

### 1-3. semantic / kinetic 구분

팔란티어 공식: *"the **semantic** elements (objects, properties, links) and **kinetic** elements
(actions, functions, dynamic security)"* — **semantic = 명사(무엇이 존재하는가),
kinetic = 동사(무엇을 바꿀 수 있는가).**

팔란티어는 자기 제품이 '시맨틱 레이어'라는 규정을 **명시적으로 거부**하는데, 그 근거가
**action/security 통합**이다.
→ **write-back·액션이 없는 프로젝트에서는 그냥 「시맨틱 레이어」라 부르는 것이 정직하다.**

### 1-4. 성과 검증 — 실패 (2026-08 기준)

**온톨로지 자체에 귀속시킬 제3자 검증 성과를 하나도 찾지 못했다.**
- Forrester TEI(평균 30% 비용절감) = **팔란티어가 의뢰한(commissioned) 연구**
- NHS FDP(£330M) = Health Foundation *"no meaningful difference"*,
  National Audit Office *"팔란티어 주장의 수치를 확인할 수 없다"*

**⇒ 「팔란티어가 성과를 냈으니 온톨로지가 효과 있다」는 논증을 쓰지 마라.**

## 2. ★ 2층 분리 원칙 (모든 도메인 공통)

| 층 | 담당 | 하는 일 |
|---|---|---|
| **1층** | **온톨로지** | 표현 · 설명 · 재사용 — 개체·링크·파생지표 정의, LLM 근거, 화면 자동 조립 |
| **2층** | **통계/ML** | 신호 선별 — 교차검증, 축소추정, 잔차 검정 |

**섞으면**: *"복잡하니까 변수가 많아야 한다" → 피처 폭발 → 과적합 → 백테스트에서만 좋은 모델*

**그리고 제품이 「예측」이 아니라 「이해·도구」라면**: 1층이 상품이고 2층은 품질관리다.
**2층 결론이 "유의하지 않다"여도 사업이 무너지지 않는다.** 이 비대칭을 의식적으로 설계하라.

## 3. 온톨로지 도입 판단

### 3-1. 유일하게 숫자 있는 정당화 — LLM 질의 정확도

Sequeda et al., arXiv **2405.11706** — 동일 DB:

| 방식 | 정확도 |
|---|---|
| SQL 스키마만 → Text-to-SQL | **16%** |
| 온톨로지/KG → Text-to-SPARQL | **54%** |
| + **OBQC**(질의가 온톨로지와 맞는지 결정론적 검사) + LLM Repair | **72%** (8%는 "모르겠음") |

보조: Atlan AI Labs — 174질의·522평가에서 거버넌스 메타데이터 제공 시 **+38%(p<0.0001)**.

⚠️ **이 증거는 "데이터에 대한 질문에 정확히 답하기"에 관한 것이지 "결과를 잘 예측하기"와 무관하다.**

### 3-2. 채택할 명분 / 채택하면 안 되는 명분

| ✅ 정직한 명분 | ❌ 거짓 명분 |
|---|---|
| 앱·리포트·LLM 해설이 **동일한 정의**를 쓴다 | 온톨로지로 **예측이 좋아진다** |
| 자연어 질의 정확도 16% → 54~72% | **복잡계라서 그래프가 답**이다 |
| 화면·콘텐츠 **자동 조립**으로 소수 인원 운영 가능 | **팔란티어 기술을 적용**했다 |
| 새 분석 추가 시 파이프라인 재작성 불요 | |

**대외 카피에 '온톨로지'라는 단어를 쓰지 마라.**
번역: *"○○을 사람이 이해하는 방식대로 데이터를 연결했습니다."*

### 3-3. ★ 벤치마킹 대상 — 팔란티어가 아니라 **BBC**

**BBC Dynamic Semantic Publishing** — 2010 FIFA 월드컵 → 2012 런던올림픽 + BBC Sport 개편 →
2014 브라질 월드컵. **SPARQL 질의로 800+ 집계 페이지 자동 생성**, BBC Sport Ontology 공개 스펙.

**핵심: 이 온톨로지는 예측하지 않는다.** 엔티티를 타입화된 링크로 잇고 그 위에서
**페이지·내비게이션·집계를 자동 생성**한다.

**BBC가 산 것은 인프라가 아니라 "객체 타입과 링크를 먼저 정의하면 페이지가 자동으로 조립된다"는
설계 원칙이고, 그 원칙은 공짜다.**

⚠️ **반면교사**: EuroLeague play-by-play 지식그래프는 **스키마만 그리고 질의를 시연하지 않아**
아무것도 아니었다. → **온톨로지를 만들기 전에 "이 온톨로지가 답해야 할 질문 20개"를 먼저 적어라.**

## 4. 저비용 스택 결정

### 4-1. 규모별 결정 트리

| 데이터 규모 | 권장 |
|---|---|
| ~수십만 행 | **DuckDB 단일 파일 + Parquet** 또는 PostgreSQL. **그래프DB 불요** |
| 계보·경로 질의 | **recursive CTE**로 충분 |
| 그래프DB 도입 | **필요가 증명될 때까지 하지 않는다** |

### 4-2. ★ "한 정의, N 소비처" — 도입의 실질 ROI

`ontology.yaml` **선언 파일 하나**가 여러 곳에 동시 공급되게 한다.

```
ontology.yaml ─┬─→ ① DB 뷰 생성
               ├─→ ② UI 라벨 · 용어 해설
               ├─→ ③ LLM 프롬프트 컨텍스트
               └─→ ④ 데이터 검증 규칙
```

**앱을 갈아엎어도, 프레임워크를 바꿔도, 다른 도메인으로 가도 살아남는 것은 이 파일뿐이다.**
**코드에 하드코딩하면 자산이 개인 머릿속에만 남고 팀원에게 이전되지 않는다.**

### 4-3. 금지·주의

- ❌ **Kuzu** — 2025-10 Apple 인수 후 **아카이브**. 커뮤니티 포크(LadybugDB)로 이관.
  **1인 프로젝트가 아카이브된 DB 위에 올리는 것은 자해**
- ❌ **RDF/OWL/트리플스토어** — 단일 소스 도메인에 과잉
- ❌ **GNN** — 표본이 수만 건 규모면 **과적합 기계**. 수년치 축적 후에만 검토
- **관할권/도메인 확장**: 온톨로지를 복제하지 말고 **클래스 상속·enum 확장**으로.
  팔란티어조차 Gotham·Foundry를 **하나의 온톨로지 엔진**으로 처리한다

### 4-4. LLM 결합 패턴 (AIP에서 베낄 수 있는 유일한 것)

온톨로지를 LLM에 **typed tool 카탈로그**로 노출한다.
팔란티어 공식: *"LLMs do not have direct access to tools; LLMs can only ask to use tools,
and these tool calls are then executed ... within the invoking user's permissions."*

→ **LLM은 제안만 하고, 실행·권한 검사는 결정론적 계층이 한다.**
2026년 MCP·function calling 표준과 구조적으로 동일하다. 차별점은 **툴 카탈로그가 정식 데이터 모델과
1:1로 묶여 있다는 것**뿐.

**구현**: ①스키마를 YAML 1개로 선언 ②시스템 프롬프트에 통째 주입 ③조회 tool 3~5개만 함수로 노출
④**LLM이 SQL을 직접 쓰지 못하게** ⑤**OBQC** — 확신 없으면 **"모르겠음" 반환**.
*틀린 숫자를 자신 있게 말하는 것보다 모른다고 하는 것이 압도적으로 안전하다.*

## 5. Forward Deployed Engineer 방법론

### 5-1. 실체 (자기서사와 분리)

**공식 축**: **Dev = "하나의 기능, 다수의 고객"** / **Delta(FDE) = "하나의 고객, 다수의 기능"**.
**Echo = Deployment Strategist**(코드를 쓰지 않고 '무엇을 만들 것인가'와 조직 내 채택 담당).
⚠️ **흔한 오해**: Echo를 Product Engineer로 아는 것. 제품 엔지니어는 **Dev**다.

공식 채용문구: *"FDE의 책임은 스타트업 CTO와 비슷하다 — 소규모 팀에서 고위험 프로젝트의
end-to-end 실행을 소유한다."*

### 5-2. ★ 핵심 한 문장

> **문제가 실제로 발생하는 물리적 장소에 가서, 사람이 지금 손으로 하고 있는 일을 자기가 대신 해 보고,
> 그 손작업을 없애는 것을 그 자리에서 만들어 다시 그 사람 앞에 놓는 사람.
> 여러 번 반복해서 나온 것만 제품으로 남긴다.**

근거: 전직 FDE 8년 회고(Nabeel Qureshi) — 에어버스 건에서 **툴루즈로 1년 이주해 공장에서 주 4일**.
*"FDE가 현장에서 cruft work를 수동으로 하고, PD 엔지니어가 그것을 자동화하는 도구를 만들었다 —
그것이 Foundry가 초기 형태를 갖춘 방식이다."* 산출물은 *"비행기 만드는 용도의 Asana"*.
코드 품질은 의도적으로 낮다 — *"일을 빨리 끝내는 코드… 기술부채와 임시방편."*

### 5-3. ★ 온톨로지는 언제 등장하는가

> **온톨로지는 "먼저 설계"도 "나중에 저절로 생김"도 아니다.
> 워크플로 하나가 요구하는 명사·동사만큼만, 그 워크플로를 끝내는 과정에서 만들어진다.
> FDE는 온톨로지를 설계하지 않고 「적출(extract)」한다.**

팔란티어 공식 안티패턴: **"kitchen sink"** — *"워크플로에 유용하고 명확한 비즈니스 의미가 있는
컬럼만 포함하라"*, *"온톨로지는 소스 데이터가 아니라 실세계를 모델링한다."*

**AI 시대의 추가 논거**: 팔란티어는 이미 온톨로지 생성·편집을 `AI FDE` 에이전트로 자동화했다.
**자동화되지 않은 것은 「무엇을 넣을지 아는 것」뿐이고, 그것은 현장에서만 나온다.**

### 5-4. 적출 절차 (3회 규칙)

1. 손으로 만든 산출물을 나란히 놓는다
2. **거기 실제로 등장한 명사·동사에만** 밑줄
3. **3장 이상에 등장한 것만** 객체·링크로 승격. 1~2회는 버린다
   (팔란티어 기준으로도 현장 발견의 약 **90%는 승격되지 않는다**)
4. 승격된 명사가 요구하는 필드만 자동화
5. **선언 파일에 저장 — 코드에 하드코딩 금지**

⚠️ **1인/소수 조직의 난점**: 팔란티어에서 "과적합해도 되는 이유"는 일반화를 남이 해주기 때문이다.
손으로 만들면서 동시에 "이건 일반화될까"를 생각하면 둘 다 망친다.
→ **시간으로 분리한다.** 현장 당일은 일반화 금지, 다음 날만 승격 판정.
**승격 판정은 만든 사람이 아닌 사람이 하는 것이 낫다.**

### 5-5. FDE 비판 (신화화 방지)

- **"대부분 회사의 대부분 FDE는 이름만 바꾼 SA(솔루션 아키텍트)다"**
- **"'사내 플랫폼에 다시 통합한다'는 부분이 실제로는 일어나지 않는다. 조금은 사기극"**
- 전 팔란티어 공급망 총괄: *"25살짜리 엔지니어를 고객 앞에 앉히는 데 문제가 있다 —
  기본 개념을 이해하지 못한다"*
- a16z의 분석: **명칭 차익(title arbitrage)** — 지위 낮던 솔루션 엔지니어를 재명명해
  **고에이전시 인재를 끌어오는 채용 해자**를 만든 것
- 채용공고 실측: FDE 공고의 **30%는 사실상 세일즈 엔지니어**, 10%는 사내툴, **60%만 진짜 빌더**
- 판별선: *"고객별 마진을 쥐어짜는 회계원 팀을 두고 있다면 당신이 하는 건 전문서비스이고,
  그냥 그렇다고 정직하게 말하는 게 낫다."*

### 5-6. FDE가 적용되지 않는 곳

First Round·CRV·a16z 공통: **PLG·소비자 제품·소액 ACV는 제외 대상.**
*"전방배치 엔지니어링은 정의상 상행(upmarket) 모션이다."*
팔란티어 고객당 평균 매출 ≈ **$4.7M**.
→ **B2C 소액 구독에 FDE 「경제학」을 적용하면 산술적으로 파산한다.
가져올 것은 경제 모델이 아니라 「순서와 규율」뿐이다.**

### 6-2. ★ 반드시 경계할 것

**① "나는 내 고객이다"의 함정**
FDE의 힘은 **「외부인의 시선 + 도메인 몰입」**의 조합인데, **창업자는 이미 도메인 안에 있어 외부인의
시선을 잃는다.** 자기 경험은 **n=1이며 데이터가 아니라 가설**이다.
→ 문서 첫 줄에 *"창업자는 표적 시장의 ○○%에 속하지 않는다"*를 적어라.

**② 전문가의 초보 난이도 과소평가**
Hinds(1999): **전문가는 초보의 어려움을 과소평가하며 실제 소요는 예측의 약 2배.**
→ **"착수 여부를 가르는 검증"을 도메인 전문가 본인이 수행하면 판정 전체가 오염된다.**

**③ 만드는 속도가 빠른 것이 위험이다**
팔란티어 FDE가 대충 만드는 이유는 제대로 만들 시간이 없어서인데, AI 도구가 있으면 정반대로
**제대로 만드는 게 더 빨라서 "빨리 만든다"가 자동으로 "제품을 만든다"가 된다.**
그건 throwaway가 아니라 **매몰비용 생성**이고, 소수 조직에는 일반화해 줄 PD팀이 없다 —
**만든 사람이 버려야 하는데, 만든 사람은 자기가 만든 걸 못 버린다.**
→ **폐기 기한을 사전에 못박아라.**

**④ 개발 속도는 해자가 아니다**
위시켓 실데이터: 프로젝트 내 코딩 비중 2023년 45% → 2026년 30%인데 **총액은 유지**.
기획/요구정리 15→20%, QA/검증 15→20%, PM 10→15%로 이동.
**"코딩 20~40배"는 프로젝트 전체로는 1.3~1.5배 레버리지.**
→ **해자는 반드시 개발 역량 밖(규제 지위·독점적 고객 접근·축적 데이터)에서 와야 한다.**

**⑤ FDE 방법론은 "무엇을 만들지"만 답한다**
**"사람을 어떻게 모을지"에는 아무 말도 하지 않는다.** 팔란티어 FDE는 고객이 이미 돈을 내고 부른
다음에 들어간다. 유통 경로가 없는 프로젝트에서는 그 공백이 그대로 남는다.

### 6-3. 지표 설계 원칙

- **임계값을 사전에 못박는다** (사후에 정하면 결과에 맞춰 조정 — 확증편향)
- **위조 불가능한 신호를 하나 포함하라** — 사용자가 **먼저 요청해 오는 것**.
  칭찬·긍정 반응은 관찰자가 옆에 있어서 나온 결과일 수 있다
- **수작업 시간의 감소 곡선**을 재라. CRV: *"고객 1인당 커스텀 작업량이 시간이 지나며 줄지 않는다면,
  그 모델은 제품 문제를 푸는 게 아니라 가리고 있는 것이다."*

## 7. 체크리스트 (프로젝트 착수 시)

**온톨로지를 만들려 할 때**
- [ ] 이 온톨로지가 답해야 할 **질문 20개**를 먼저 적었는가?
- [ ] 예측 개선을 기대하고 있지 않은가? (기대하면 안 됨)
- [ ] 소스 데이터가 아니라 **실세계**를 모델링하고 있는가?
- [ ] 객체명이 API/테이블 필드명과 1:1로 대응하지 않는가? (대응하면 kitchen sink)
- [ ] **현장에서 실제로 나온 명사**가 하나라도 들어 있는가?
- [ ] 선언 파일(YAML) 하나가 **N개 소비처**에 공급되는 구조인가?
- [ ] 그래프DB가 정말 필요한가? (수십만 행이면 불요)

**FDE 방식으로 일하려 할 때**
- [ ] 대기가 필요한 것을 **먼저** 발사했는가?
- [ ] **하나의 결정 순간**을 골랐는가? (워크플로 전체가 아니라)
- [ ] 첫 산출물이 **버릴 수 있는 것**인가? (종이 > 앱)
- [ ] 자기 자신을 표본으로 쓰고 있지 않은가?
- [ ] 판정 임계값을 **사전에** 정했는가?
- [ ] **위조 불가능한 지표**가 하나 있는가?
- [ ] 폐기 기한을 못박았는가?
