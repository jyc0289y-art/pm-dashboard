> **추가 일자**: 2026-05-06 (사용자 지시: "내 노동력을 줄이기 위해 시스템 만들고 있는데 의미없는 검수 요청은 노동력 낭비. 검수가 의미있는지 사전 검토")

### 게이트 G1 — 산출물 최신성

- 위반 시: "재빌드 안 됨" 자동 감지 → 빌드 트리거

- **자막 동기화**: 자막 timing이 audio 발화와 ±200ms 이내

## 사용자 검수 요청 의무 (User Verification Interface Rule)

> **추가 일자**: 2026-04-17 (사용자 지시: "프로젝트 중단 원인은 직접 검증 요청 단계 — HTML로 게시하고 클릭 피드백")

**시각/청각 산출물(영상·이미지·HTML·문서)을 사용자에게 검수 요청할 때 텍스트 묘사로만 끝내지 않는다. 반드시 사용자가 클릭/선택으로 피드백을 줄 수 있는 인터페이스를 제공한다.**

### 규칙 1: 검수 페이지 자동 생성 의무
검수 대상이 **영상·이미지·다층 시각물**인 경우, 다음을 포함한 단일 HTML 페이지를 생성한다:
- **헤더에 `P{N} · {프로젝트명}` 식별 표기 필수**(2026-06-11 P38: 여러 프로젝트 동시 보고 시 구분 — 제목 또는 부제 맨 앞에)
- 산출물 직접 재생/표시 (HTML5 video, img tag)
- **같은 시점 / 같은 좌표 비교** (PREV vs NEW 그리드)
- **시점별/항목별 체크리스트** (good/needs-fix/critical 라디오 + 자유 코멘트)
- **피드백 복사 버튼** → 구조화 텍스트(JSON/Markdown)를 클립보드로 → 사용자가 채팅창에 붙여넣기 가능

### 규칙 2: 표준 위치
- HTML 산출물: `{프로젝트}/docs/qa_review/qa_{YYYYMMDD_HHMMSS}_{설명}.html`
- 의존 자산(프레임 이미지·복사 영상): 같은 디렉토리 또는 `{ts}_assets/` 하위
- **단일 폴더로 자가완결** (브라우저로 열면 외부 의존 없이 동작)
- **★프로젝트 식별 배지 필수 (2026-06-11, P40에서 격상)**: 모든 검수 페이지·HTML 보고서 머리에 **`P{N} · {프로젝트명}` 배지**를 눈에 띄게 표시 + `<title>`에 `[P{N}]` 접두. 여러 프로젝트가 동시에 보고하면 사용자가 구분 불가(P38·P40 혼동 사례).

### 규칙 3: 글로벌 스크립트
- `~/.claude/scripts/generate_qa_page.py` 사용 (없으면 P21 FEP `EP01_forced_compliment/qa_review_page.py` 참조)
- 입력: NEW/PREV 영상 경로 + 비교 시점 리스트 + 체크리스트 항목
- 출력: 단일 HTML 페이지 + 자동 브라우저 오픈 (`open` 명령)

### 규칙 4: 사용자 피드백 형식
HTML 페이지의 "피드백 복사" 버튼은 다음 형식의 텍스트를 클립보드에 넣는다:
```markdown
## QA 피드백 — {빌드명}
- 115s 03_validation: ✅ 정상 / 🟡 위치 어색 / 🔴 자막 가림
- 280s 다층 자막: 🟡 Type D와 Type F 겹침
- 자유 코멘트: ...
```
사용자가 이를 채팅창에 붙여넣으면 AI가 즉시 항목별 수정 진행.

### 규칙 5: 텍스트만의 검수 요청 금지
- ❌ "확인해주세요", "괜찮은지 봐주세요" 만 보내고 작업 종료
- ✅ HTML 페이지 경로 + `open` 명령 + 체크리스트 항목 미리보기 함께 제공

### 규칙 6: 철저한 캡쳐 — 시간 제약 사용자를 위한 피드백 준비 (P36에서 격상, 2026-06-06)
> 사용자 지시: "캡쳐가 꼼꼼히 들어갔다면 피드백으로 회신된 내용이 훨씬 많았을 것. 사람은 시간이 항상 제약돼서, 미리 준비해줄 수 있는 부분을 챙겨주지 않으면 의지가 있어도 피드백을 줄 수 없다."

**핵심 원칙: 피드백의 병목은 사용자의 의지가 아니라 시간이다. 피드백 비용을 최소화하도록 미리 다 준비한다.**

1. **기능·상태별로 충분히 캡쳐**: 각 신규 기능을 *대표 화면 1장*으로 끝내지 말 것. 핵심 상태(예: 신생/성장/고레벨, 정상/위기, before/after, 빈/채워진)별로 스크린샷을 담아 사용자가 *그 자리에서* 보고 판단할 수 있게 한다. 자율 빌드(사용자 부재) 중일수록 더 꼼꼼히.
2. **검수 페이지에 스크린샷 인라인 임베드**: 직접 앱/기기를 켜지 않아도 페이지만 보면 변경을 한눈에 — 텍스트 설명 + 캡쳐 이미지를 항목마다 함께. (네이티브 앱은 시뮬레이터 캡쳐를 `{ts}_assets/`에 저장 후 `<img>`로 임베드.)
   - **★배치 원칙 (2026-07-12 P40 TRAP-008→P48 TRAP-006 재발로 전역 격상)**: 캡쳐를 상단 갤러리에 몰아넣고 문항과 분리 금지. **각 검수 문항 바로 아래에 그 문항 전용 크롭(핵심 영역만) + '볼 곳' 1줄 + 전→후 델타를 동거 배치**, 크롭 클릭=원본 전체 오버레이. "문항↔캡처 매칭을 사용자가 하게 만들면 검수 부하 절감 실패"(오너 원문). 게시 전 크롭 전수 Read 자가 검사 의무(오크롭 적발). ⚠️sips 크롭 offset 0 0 금지(중앙 크롭 오동작 — 최소 2 2).
   - **★목업·프로토타입은 「전후 대조」로 제공 (2026-08-12 P57 오너 지시로 격상)**: 오너 원문 — *"이 질문 뿐만 아니라 **전체적으로 다음부터는 목업을 변경전후를 놓고 대조해볼 수 있게** 제공해줘. **찾아내는데 시간이 많이 걸려**."*
     ⓐ **신안만 보여주지 말 것.** 신안 단독 화면은 오너에게 *"무엇이 달라졌는지 먼저 찾아내라"*는 숙제를 떠넘긴다 — 판정 이전에 **탐색 비용**이 발생하고 그것이 회신을 지연시킨다(위 ★배치 원칙과 같은 계열의 실패: 매칭을 사용자에게 시키면 검수 부하 절감 실패).
     ⓑ **제공 형태 3종 중 최소 하나**: ①**나란히**(좌=현행 / 우=신안, 같은 상태·같은 데이터) ②**겹쳐 토글**(같은 자리에서 A/B 전환 — 위치·크기 변화를 보는 데 가장 강함) ③**변경점 표식**(달라진 요소에 배지·테두리 + 「무엇이 왜」 1줄). 위치·크기가 쟁점이면 ②를 우선.
     ⓒ **"현행"은 재현물이 아니라 실제 현행이어야 한다** — 기억으로 그린 현행은 대조를 무의미하게 만든다. 실제 화면 캡처 또는 현행 코드의 실측값에서 만들 것.
     ⓓ 정량 변화가 있으면 **숫자를 함께**(예: 사진 면적 31.75% → 63.3%). 대조는 눈으로, 확인은 숫자로.
     ⓔ 적용 범위: 검수 페이지·프로토타입·목업·리디자인 제안 전부. **판정을 요청하는 모든 시각 산출물**.
3. **체크리스트는 항목별 ✅/🟡/🔴 + 코멘트 + 복사 버튼**(규칙 1·4). 사용자가 *해본 것만* 체크하고 부분 회신 가능하게.
   - **★코멘트 입력란 = 여러 줄 `<textarea>` (2026-07-15 P49 오너 지시로 격상)**: 한 줄 `<input>` 금지 — 오너 원문 *"코멘트 입력란 줄바꿈해서 코멘트 전체를 보고 편집하기 편하게"*. 최소 3행·세로 리사이즈 허용(`resize:vertical`)·입력에 따라 자동 확장 권장. 긴 피드백이 검수의 핵심 산출물인데 한 줄 칸은 작성 자체를 억제한다.
   - **★결의·요약 문항에는 근거 딥링크 동반**(누적 보고서 규칙 8과 동일 취지): 검수 문항이 결의·수치를 요약해 묻는다면 "어느 회의록 어느 절"인지 링크를 문항 옆에 둔다. 오너가 세부를 못 찾으면 회신 불가.
4. **'사용자만 판단 가능한 것' vs 'AI가 이미 검증한 것' 분리 표기**(G5): 사용자의 짧은 시간을 *판단이 필요한 곳*에만 쓰도록.
5. **자율 작업(사용자 부재) 종료 시**: 그동안의 모든 변경을 한 검수 페이지로 묶고, `open`까지 해두어 사용자가 돌아오면 *즉시* 검토 가능하게 준비.

11. **★모든 라운드에 시각 증거 의무 — 글자만 있는 라운드 금지 (2026-07-27 P50 오너 지시로 격상)**: 오너 원문 — *"누적보고서에 **텍스트만 주저리주저리 적지말고 그 턴의 결과물들좀 삽입해**. 봐도 **기억도 안나** 그냥 글자만 써놓으면. 결과물이 이미지면 그걸 첨부하고, **결과물이 이미지가 아니더라도 어떤 캡쳐나 시각자료를 넣어줘야 기억이 날거 아냐**."*

    - **앱·UI 변경** → 시뮬레이터/기기 스크린샷 (전·후 쌍)
    - **수치·측정·통계** → 표를 그린 차트 PNG 또는 결과표 렌더 이미지 (matplotlib·PIL·HTML→캡처 무엇이든)

    - **터미널 작업(빌드·배포·검증)** → 그 출력의 캡처 이미지 (텍스트 붙여넣기가 아니라 **그림으로**)
    - **문서·기록물** → 그 문서의 첫 화면 렌더 캡처
    - **분과·패널 회의** → 결의 요지를 담은 카드형 도식
    → 진짜로 만들 게 없으면 **그 턴에 무엇이 달라졌는지 보여주는 전·후 비교 그림을 만들어라**. "만들 시각자료가 없다"는 대개 **안 만든 것**이다.

12. **★「✅ 작업 추적」 탭 의무 — 지시 누락을 오너가 직접 확인할 수 있게 (2026-07-27 P51 오너 지시로 격상)**: 오너 원문 — *"작업누락방지 추적에관한 사항도 누적보고서에 누적기록해서 내가 확인할 수 있도록 하고 전역지침에 반영해."*

    **⓪ 왜 필요한가**: 어시스턴트의 내부 작업 목록(TaskCreate/TaskList)은 **오너가 볼 수 없고, 컨텍스트 리셋으로 통째로 사라진다**(P51 실사례: 등록한 10건이 전부 소실됐고 어시스턴트는 그걸 알고도 재등록하지 않았다). 추적 장치가 어시스턴트 머릿속에만 있으면 누락을 오너가 뒤늦게 발견하게 된다. **보고서에 남겨야 추적이 성립한다.**

    **① 누적 보고서에 `meta["task_ledger"]`를 채운다** (전역 엔진이 「✅ 작업 추적」 탭으로 렌더):
    ```python
    task_ledger = {
      "updated": "YYYY-MM-DD HH:MM",
      "note": "상단 안내 1줄",
      "rounds": [                      # ★ 누적 — 과거 턴을 지우지 않는다
        {"turn": "r2", "date": "...",
         "given":  ["이 턴에 오너가 준 지시 (원문에 가깝게)"],

         "open":   ["미완 — 다음 턴 이월"],
         "missed": ["누락했다가 발견한 것"]},   # ← 정직 표기, 삭제 금지
      ]}
    ```
    엔진이 **최신 라운드의 `open`을 맨 위에 크게** 띄우므로, 오너는 탭 하나만 열면 "지금 뭐가 밀려 있나"를 즉시 본다.

    **② 매 턴 갱신 의무** — 라운드를 추가하는 턴마다 `task_ledger`에도 그 턴 스냅샷을 append한다. 대시보드(규칙 10)와 같은 취급이다. 라운드만 쌓고 원장을 방치하면 규칙 위반.

    **③ `missed`는 반드시 남긴다** — 누락을 발견해 처리했더라도 **기록을 지우지 않는다**(콘텐츠 보존 규칙·정직 표기와 동일 취지). 같은 종류의 누락이 반복되는지는 이 칸을 시간순으로 봐야만 드러난다.

    **④ 내부 작업목록과 이중화** — TaskCreate/TaskList는 계속 쓰되, **보고서 원장이 정본**이다. 컨텍스트 리셋으로 내부 목록이 비면 **보고서 원장에서 복원**한다.

13. **★회신 페이지도 누적 보고서로 상신 — 「📮 회신 페이지」 탭 의무 (2026-07-28 오너 지시로 격상)**: 오너 원문 — *"앞으로 **회신용 페이지도 누적보고서로 상신**하도록 하고 **그동안 모든 회신페이지도 누적보고서에 포함**시키도록 하고 전역지침에도 반영해서 다른 프로젝트에도 전파시켜줘."*

    **⓪ 왜 필요한가**: 검수·회신 페이지를 매번 따로 발행하면, 오너는 회신하려 할 때마다 **어느 채팅에서 받은 어떤 파일이었는지 찾아다녀야** 한다. 회신 이력이 채팅에 흩어지면 "무엇에 답했고 무엇이 아직 미회신인지"를 아무도 모른다. 누적 보고서가 **회신 창구의 정본**이 되어야 이 비용이 사라진다.

    **① 회신 페이지는 누적 보고서로 상신한다** — 검수 페이지를 별도 발행하고 끝내지 않는다. ⓐ 그 턴의 라운드에 **회신 페이지 링크(또는 임베드)를 함께 넣고** ⓑ 보고서에 **「📮 회신 페이지」 탭**을 두어 전체 이력을 표로 누적한다. 검수 페이지 자체는 계속 만들되(피드백 수집 UI가 필요하므로), **상신 경로는 누적 보고서로 일원화**한다.

    **② 회신 원장 필수 항목** — 발행일시 · 페이지명(파일명) · 위치(프로젝트/드라이브) · 검수 대상 · **상태** · **오너 회신 요지** · 파일 존재 여부.

    **③ 3상태 추적** — `발행`(회신 대기) → `회신완료`(오너 응답 수신, 요지 기록) → `반영완료`(응답을 산출물에 반영). **미회신 건은 「📊 한눈에」 대시보드의 「결정 대기」에도 함께 노출**한다(규칙 10과 한 쌍). 상태가 `발행`인 채로 2턴 이상 머물면 보고에 그 사실을 명시한다.
    ⚠️ **엔진이 자동 주입하지 않는다** — 대시보드는 생성기가 직접 쓰는 HTML 문자열이므로(`meta["dashboard"]={"html":…}`), **회신 원장 갱신과 대시보드 갱신은 각각 수기 작업 2회**다. 둘 중 하나만 하면 규칙 위반이며, 오류 없이 조용히 어긋난다. 회신 상태를 바꿀 때마다 대시보드도 함께 고쳤는지 그 턴에 확인한다.

    **④ 과거 회신 페이지 전량 소급 편입** — 프로젝트에 이미 발행된 검수·회신·브리핑 페이지는 **전부 찾아 원장에 등재**한다(폐기·대체된 것도 상태를 달아 남긴다 — 콘텐츠 보존·정직 표기와 동일 취지). 소급 편입이 안 된 상태는 **규칙 위반 상태**다.

    **⑤ 구현** — 전역 엔진 `session_report.py`의 `custom` 라운드로 「📮 회신 페이지」 섹션을 만들고, 각 라운드 dict에는 그 턴의 회신 페이지 경로를 `report` 본문 또는 `figs`(페이지 캡처)로 함께 싣는다. 회신 페이지가 대용량 HTML이면 링크 + 캡처로 대신한다.

    **⑥ ★회신 페이지와 「오너 회신 내용」을 그 턴의 라운드 페이지에 함께 싣는다 (2026-07-29 P52 오너 지시로 추가)**: 오너 원문 — *"누적보고서에는 **이런 회신용 페이지도 각 턴별페이지에 포함**되어야해. **각 턴별 페이지에 나의 회신내용도 같이 기록**해줘."*
    - **ⓐ 물은 턴**: 회신 페이지를 발행한 라운드 본문에 **무엇을 물었는지(문항 요약표) + 페이지 경로**를 싣는다. 「📮 원장」 탭에만 있으면 안 된다 — 원장은 *전체 이력*을 보는 곳이고, 라운드는 *그 턴에 무슨 일이 있었나*를 보는 곳이다.
    - **ⓑ 답한 턴**: 오너 회신을 받으면 **회신 원문(선택지 + 코멘트)을 그 턴 라운드에 그대로 인용**하고, 각 항목이 **설계·작업에 어떻게 반영됐는지**를 나란히 적는다(선택 → 조치 대응표). 요약만 남기고 원문을 버리지 않는다(콘텐츠 보존).
    - **ⓒ 원장 갱신 동시 수행**: 같은 턴에 「📮 원장」의 상태(발행→회신완료→반영완료)와 「📊 한눈에」의 결정 대기 항목도 함께 고친다(③과 한 쌍 — **수기 3곳**이며 하나만 하면 조용히 어긋난다).
    - **이유**: 오너가 나중에 되짚을 때 「내가 무엇을 질문받았고, 뭐라 답했고, 그래서 무엇이 바뀌었나」가 **한 페이지 안에서** 끝나야 한다. 탭을 오가며 대조하게 만들면 규칙 10(판단 비용 절감)의 취지를 무너뜨린다.

14. **★회신 페이지는 「클릭하면 열리고, 쓴 답이 남아야」 한다 (2026-07-29 P53 오너 지시로 격상)**: 오너 원문 — *"회신 페이지에서 해당 회신파일을 누르면 회신페이지가 뜨도록 만들어줘야지. **나보고 찾아가서 하란거야?** 그리고 내가 회신을 하면 **다음번에도 회신했던 내용을 확인할 수 있도록** 회신페이지에서 그 파일을 누르면 내가 회신했던 내용도 함께 뜨게 해줘. html 자체에 저장기능이 있어도 좋고."*

    **⓪ 진단**: 규칙 13은 회신 원장을 *만들라*고만 했지 **열리는지·남는지**를 규정하지 않았다. 그 결과 원장에 파일 **경로가 글자로만** 적히고(오너가 Finder로 찾아가야 함), 답변은 **메모리에만** 있어 페이지를 닫으면 소멸했다. 오너가 30분 들여 쓴 답이 사라질 수 있는 구조였다.

    **① 원장의 페이지명은 반드시 클릭 링크**: `<code>경로</code>` 텍스트 금지 → `<a href="상대경로">제목</a>`. 누적 보고서와 회신 페이지는 같은 프로젝트 안이므로 `../qa_review/…` 상대경로가 `file://`에서 그대로 열린다.
    - **게시 전 죽은 링크 기계 검사 의무**: 「링크 문자열이 있는가」가 아니라 **「`<a>` 태그로 렌더되었고 그 대상 파일이 실제로 존재하는가」**를 검사한다. (P53 실사례: f-string 중괄호 이스케이프가 이중으로 걸려 링크가 `{_rows}` 리터럴로 출력됐는데, 문자열 존재 검사는 **전 항목 통과**했다)

    **② 회신 페이지는 고정 파일명 — 타임스탬프 규칙의 의도적 예외**: 회신 페이지는 **오너가 반복해서 열고 답을 이어 쓰는 대화형 폼**이다. 파일명이 매번 바뀌면 ⓐ원장 링크가 깨지고 ⓑ오너가 옛 파일을 열어 **답이 사라진 것처럼** 보인다. → `{프로젝트}/docs/qa_review/회신_제{N}차.html` 처럼 **고정 경로**를 쓰고, 산출물 보존 책임은 **회신 원장**이 진다. 구판은 삭제하지 말고 `_superseded/`로 이관 + 사유 README.

    **③ 답변 보존 3중 안전망 (한 겹에 의존 금지)**:
    | 층 | 방식 | 약점 |
    |---|---|---|
    | 1 | **자동 저장**(localStorage) — 입력 즉시 저장·재방문 시 복원 | Safari는 `file://`에서 **막을 수 있다**(버전 의존) |
    | 2 | **답변 파일 저장/불러오기**(JSON을 다운로드 폴더로) | 오너가 버튼을 눌러야 함. 단 **어시스턴트가 그 파일을 직접 읽으므로 붙여넣기조차 불필요** |
    | 3 | **원장 박제** — 수신한 회신을 기록물에 적고, **다음 발행 시 각 문항 안에 「지난 회신」으로 함께 표시** | 어시스턴트가 기록해야 반영 |
    - 저장 키는 **파일 경로와 무관한 고정 키**(예: `P53_reply_r1`)로 잡아, 페이지를 재발행해도 답변이 살아남게 한다.

    **④ 1층이 막히면 화면이 경고한다 — 조용한 실패 금지**: `localStorage` 접근을 `try/catch`로 감싸 **성공/실패를 상태 표시줄에 정직하게 출력**한다. 막혔으면 *"이 브라우저는 자동 저장이 막혀 있습니다 — [답변 파일 저장]을 눌러 주세요"*를 띄운다. 조용히 실패하면 오너는 저장된 줄 알고 창을 닫는다.

    **⑤ 진행 상태 상시 표시**: 화면 하단 고정 막대에 **「N / 전체 항목 답하심 · 자동 저장됨 HH:MM」**. 답한 항목은 시각적으로 표시(체크·테두리)해 **일부만 답하고 나중에 이어 하기**가 가능함을 알린다.

    **⑥ 게시 전 「저장→닫기→다시 열기」 왕복 기능 시험 의무**: **문법 통과는 요구 충족이 아니다.** 오너 요구가 「다음번에도 확인」이면 그 왕복을 실제로 돌려 봐야 답이 된다. 외부 라이브러리 없이(다운로드 승인 불요) 최소 DOM을 만들어 페이지의 실제 스크립트를 실행하는 시험을 짠다 — 저장가능/저장막힘/재방문복원/회신문생성 4군. 정본: P53 `docs/qa_review/test_reply_persistence.js`.

    **⑦ ★링크가 「정상」이어도 안 열린다 — 회신 UI는 보고서 안에 임베드한다 (2026-07-29 P50 실측으로 추가)**: 오너 원문 — *"회신페이지는 잘 만들어졌는데 **회신할 파일을 클릭하면 안열려**. 확인해서 조치해줘"* / *"**다른 프로젝트에서도 동일증상**이야"*
    - **⓪ ①의 전제가 깨진 사례**: ①은 *"`../qa_review/…` 상대경로가 `file://`에서 그대로 열린다"*를 전제한다. **그 전제가 실제로 깨졌다.** P50에서 브라우저 콘솔로 전수 확인한 결과 — `<a>` 태그로 렌더됨 ✓ / `href` 해석 결과가 정확한 절대 URL ✓ / **그 URL로 직접 이동하면 대상 파일이 정상 렌더**(제목·본문·오디오 3개) ✓ / 클릭 이벤트를 가로채는 JS 없음(`defaultPrevented: false`) ✓ / `pointer-events:auto`, 겹친 요소 없음 ✓. **모두 정상인데 오너 환경에서는 열리지 않았다.**
    - **① 그러므로 「죽은 링크 검사 통과」는 열린다는 보장이 아니다**: ①의 기계 검사(태그 렌더 + 대상 파일 존재)를 **전부 통과하고도** 오너는 회신을 못 한다. 로컬 파일 간 이동은 브라우저·보안설정·iCloud 동기화 상태 등 **어시스턴트가 관측할 수 없는 변수**에 걸린다. 원인 규명에 매달리기보다 **의존 자체를 없애는 것이 옳다.**
    - **② 조치 — 회신이 필요한 항목은 보고서 안에서 완결시킨다**: 「📮 회신 페이지」 탭의 **대기 중 항목**은 링크만 걸지 말고 **회신 UI를 누적 보고서에 직접 임베드**한다. 오디오·이미지는 **data URI**로, 버튼은 **인라인 `onclick`**으로(외부 `<script>`는 `innerHTML` 주입 시 실행되지 않는다). 파일을 열 필요 없이 **그 자리에서 재생·선택·복사**가 끝나야 한다.
    - **③ 링크는 보조로만 남긴다**: 과거 발행분(아카이브)은 링크 + **「경로 복사」 버튼**을 함께 둔다. 링크가 안 열려도 경로를 복사해 Finder·터미널로 갈 수 있다.
    - **④ 검증 방법**: 브라우저에서 실제로 `show('replies')` → 오디오 개수·`src` 유효성·라디오·버튼 클릭 → **회신문이 실제로 생성되는지**까지 확인한다. 링크 문자열 검사로 갈음하지 말 것(①의 교훈과 동일 계열).
    - **⑤ 이유**: 회신 페이지의 목적은 *발행*이 아니라 **오너의 답을 받는 것**이다. 한 단계라도 «오너가 파일을 찾아 열어야» 하면 그 단계에서 회신이 멈춘다. 규칙 13·14가 겨냥한 «찾아가서 하란거야?»가 링크 형태로 되살아난 것이다.

    **⑨ ★⑦의 진단은 틀렸다 — 진짜 원인은 「보고서가 너무 커서 안 열리는 것」이었다 (2026-07-29 P50 실측 정정)**: ⑦을 적용한 뒤에도 오너는 *"여전이 회신페이지가 열리지 않아 회신 못하고있어. **P53의 회신페이지 방금 성공했으니 참조해줘**"*라고 했다. 두 페이지를 재보니 답이 나왔다 — **P53 성공작 445KB / P50 누적 보고서 56.8MB (128배)**. 링크도, 브라우저 보안설정도, iCloud도 아니었다. **base64로 이미지·오디오를 쌓아 올린 누적 보고서가 브라우저에서 열리지 않는 크기가 된 것**이다.
    - **⓪ 왜 오진했나**: ⑦은 링크 관련 항목을 전부 검사해 「모두 정상」을 확인하고는, 설명되지 않는 부분을 *「관측할 수 없는 변수」*로 봉인했다. **정작 파일 크기는 한 번도 재지 않았다.** 관측 가능한 것이 남아 있는데 관측 불가로 결론지은 것 — 「정황 추론을 관측으로 착각」 계열의 변종이다. **증상이 «안 열린다»이면 링크보다 먼저 `ls -la`로 크기를 재라.**
    - **① 조치 — 회신 페이지는 누적 보고서와 분리한 「가벼운 단독 파일」로 만든다.** ⑦의 «보고서 안에 임베드»는 **정반대 처방이었다**(가장 무거운 문서에 오디오를 더 얹는다). 정본은 **P53 방식** — `docs/qa_review/회신_제N차.html`, **목표 200KB 이하**, 오디오·이미지는 base64가 아니라 **같은 폴더의 상대경로 파일**로 두고 `preload="none"`.
    - **② 누적 보고서는 「추적」, 단독 회신 페이지는 「회신」** — 규칙 13의 상신 일원화는 유지하되(보고서 「📮」 탭에 원장·링크는 그대로), **회신 행위 자체는 가벼운 단독 파일에서** 끝낸다. 보고서는 시간이 갈수록 반드시 무거워지므로, 회신 창구를 거기 두면 **언젠가 반드시 다시 막힌다.**
    - **③ 크기 상한을 자가 검사한다**: 생성기가 산출물 크기를 출력하고 **회신 페이지 >1MB 또는 누적 보고서 >20MB면 stderr 경고**. 보고서가 한계를 넘으면 base64 임베드를 **외부 파일 참조로 전환**하거나 라운드를 분할한다.
    - **④ 검증**: 브라우저에서 실제로 열어 **①문항·오디오·라디오 개수 ②오디오 `loadedmetadata` 성공 ③실제 클릭 → 회신문 생성**까지 확인(⑦-④ 유지). 여기에 **⓪크기 측정**을 앞에 붙인다.
    - **⑤ P53에 전파**: P53은 ⑦에 따라 «보고서 내 임베드»로 전환하려 했으나 **그럴 필요가 없다** — P53의 445KB 단독 페이지가 이미 정답이며, 그것이 ⑨의 정본 사례다. 임베드 전환을 진행 중이면 중단하고 현행 방식을 유지하라.

16. **★대기 작업 원장 — 채팅에 «표»로, 우선순위 순으로, 선후관계까지 (2026-08-21 P64 오너 지시로 격상)**: 오너 원문 — *"남은 대기도 채팅에 항상 표로 표시하고 **우선순위 순(진행예정 순)**으로 표시해줘. 필요하면 내가 우선순위 조정할건데 **대기작업간 선후관계가 있어서 선행작업이 이뤄져야 하는 관계가 있다면 참조할 수 있게 표에 함께 표시**해주고 **누적보고서에도 매턴 함께 기록**해줘."* (같은 날 선행 지시: *"채팅에서 진행률은 항상 표로 보고해."*)

    **① 채팅 매 턴 «남은 대기» 표 (필수)** — 진행률 표 바로 아래에 둔다. 최소 컬럼 5개:

    | 순위 | 대기 작업 | 왜 이 순위 | 선행조건 | 상태 |
    |---|---|---|---|---|
    | 1 | 웹앱 UI 개선 | 오너가 «성적서보다 급하다»고 지정 | — (바로 착수 가능) | ▶ 착수 |
    | 2 | 성적서 정리 v1.5 | 실사용 요구지만 경로 대기 | **①스캔폴더 경로(오너)** | ⏸ 대기 |
    | 3 | 원격 이중화 | 단일 장애점 해소 | **②비밀 처리 방침(오너)** | ⏸ 대기 |

    **② 정렬은 «진행 예정 순»** — 중요도 순이 아니라 **실제로 다음에 손댈 순서**다. 오너가 순위를 바꾸면 그 즉시 표를 재정렬하고, 바뀐 사실을 다음 턴 표에 «(오너 조정)»으로 표기한다.

    |---|---|---|
    | ✅ **된다** | 지금 쓸 수 있고 실측으로 확인함 | 무엇을 확인했는지 한 줄 |

    | ⛔ **안 함** | 이번 범위에서 의도적으로 뺌 | **왜 빼는지**(범위 폭주 방지 근거) |

    **② «임시»를 숨기지 않는다 — 먼저 말한다.** 어색한 부분을 오너가 발견해 지적하게 두면, 오너는 «이걸 못 봤나»라고 생각하며 신뢰를 잃는다. *"지금은 한 칸씩 묻는 방식이라 불편합니다 — 한 창에서 고르는 형태로 바꿀 예정입니다"*처럼 **내가 먼저 이름 붙여** 둔다. 이미 아는 결함을 «발견당하는» 것이 가장 나쁘다.

    **③ 세분화 수준은 «오너가 지시를 참을 수 있을 만큼»**. «웹앱 개선»처럼 뭉뚱그리면 오인이 그대로 남는다. 화면·기능 단위로 쪼개 각각에 위 4구분을 단다. 오너가 표를 보고 *"아 저건 이미 계획에 있구나"*라고 판단할 수 있으면 충분하다.

    **④ 놓아두는 자리**: ⓐ채팅 보고(규칙 16 대기 표 **바로 아래**) ⓑ누적 보고서의 그 라운드 ⓒ산출물이 화면이면 **화면 안에도**(예: 제목 옆 «v2 · 만드는 중», 미구현 버튼에 «준비 중» 표시) — 오너가 산출물만 열어도 알 수 있어야 한다.

    **⑤ 상태가 바뀌면 그 턴에 갱신** — 🟡→✅, ⏳→🟡 로 옮기고, 바뀐 것을 «이번 턴 변화»로 표시한다(규칙 15·16과 같은 취급). 다 ✅가 되면 표를 내린다.

    **⑥ 이 규칙은 «변명 목록»이 아니다** — 못 한 것을 나열해 면책받으려는 것이 아니라, **오너가 헛지시를 하지 않도록 하는 도구**다. 그러므로 ⓐ항목마다 «언제/어느 순서»가 붙어야 하고 ⓑ⛔(안 함)에는 반드시 근거가 있어야 하며 ⓒ목록이 턴마다 줄어들어야 한다. 줄지 않는 목록은 이 규칙의 실패다.

18. **★진행률·대기작업·성숙도 3종을 누적보고서 «매 라운드»에도 동거시킨다 (2026-08-25 P42 오너 지시로 격상)**: 오너 원문 — *"누적보고서에도 **진행률과 대기작업표, 성숙도 매 턴 넣어서 함께 보고**하도록 전역지침, 그록비침습전파 개정해. **누적보고서의 핵심 가치와도 일치**해."*

    **⓪ 진단 — 규칙 15·16·17이 «채팅에만» 걸려 있었다.** 세 규칙은 각각 진행률·대기작업·성숙도를 규정했지만, 누적보고서 쪽 의무는 규칙 15-⑤(라운드 `progress` 스냅샷)뿐이고 **대기작업표와 성숙도표는 채팅에만 남았다.** 채팅은 흐르고 압축되어 사라진다 — 몇 턴 뒤 그 라운드를 열었을 때 «그때 무엇이 막혀 있었나 / 무엇이 아직 안 되는 상태였나»를 알 수 없다. **보고서가 추적의 정본인데 절반만 실린 셈**이고, 이는 규칙 11(글자만 있는 라운드 금지)이 겨냥한 «되짚어도 기억 안 남»과 같은 실패다.

    **① 매 라운드 3종 세트 의무** — 라운드를 추가하는 턴마다 그 라운드에 함께 싣는다:
    - **진행률**: 라운드 dict의 `progress` 필드(규칙 15-⑤) — 엔진이 자동 렌더
    - **대기작업표**: 그 턴 시점의 «순위 · 작업 · 왜 이 순위 · 선행조건 · 상태»(규칙 16 형식 그대로, **한 행 = 한 작업**)
    - **성숙도표**: 미완 산출물이 있는 동안 «✅된다 / 🟡임시 / ⏳아직 / ⛔안 함»(규칙 17)

    **② 채팅과 보고서는 «같은 표»** — 이중 작성이 아니다. 채팅 보고에 쓴 표를 **그대로** 라운드 `report` 본문에 넣는다. 내용이 갈라지면 어느 쪽이 정본인지 알 수 없게 되므로, 갈라진 것을 발견하면 보고서를 정본으로 맞춘다.

    **③ 시점 박제가 목적** — 「📊 한눈에」 대시보드와 「✅ 작업 추적」 탭은 **최신값으로 덮인다**. 라운드에 실린 3종은 **그 턴 당시의 스냅샷**으로 남아야 한다(규칙 15-⑤와 같은 취지). 오너가 아무 라운드나 열어도 «그때 어디까지 왔고, 무엇이 밀려 있었고, 무엇이 아직 미완이었나»가 한 화면에서 끝나야 한다.

    **④ 구현** — 엔진 변경 불요. 라운드 dict에 `progress` 필드 + `report` 본문에 표 2개(대기·성숙도)를 마크다운/HTML로 넣으면 된다. 「✅ 작업 추적」 원장(규칙 12)의 그 턴 `open` 항목과 **같은 순서·같은 선행조건**을 유지한다(규칙 16-④와 한 쌍 — 어긋나면 조용히 틀어진다).

    **⑤ 자가 검사** — 생성기가 **`progress` 없는 라운드**와 **대기표 없는 라운드**를 세어 stderr로 경고한다(규칙 11-④의 figs 검사와 같은 계열). 소급 적용: 이 규칙 도입 이후의 라운드가 대상이며, 그 이전 라운드는 재구성 가능한 범위에서 채운다.

    **⑥ 왜 이것이 «누적보고서의 핵심 가치»인가** — 보고서의 존재 이유는 «오너가 나중에 되짚어 판단하는 것»이다. 진행률만 있고 무엇이 막혀 있었는지가 없으면 그 판단을 재구성할 수 없고, 성숙도가 없으면 «그때 이미 계획에 있던 것»을 새 지시로 착각하게 된다(규칙 17-⓪의 오인 지시가 시간을 건너 재발한다).

19. **★스토리지 게이지 — 디스크도 진행률처럼 매 턴 시각화 (2026-08-25 P42 오너 지시로 격상)**: 오너 원문 — *"스토리지상태도 진행률처럼 매번 시각화해서 보고해. 스토리지 보고도 전역지침 반영 및 그록비침습전파 조치"*

    **⓪ 진단** — 디스크는 **한 번 꽉 차면 그 자리에서 모든 작업이 멈추는** 자원인데, 그동안 «여유 몇 GB» 한 줄로만 보고됐다. 오너는 숫자 하나로 «지금 괜찮은지 / 곧 위험한지 / 무엇이 먹고 있는지»를 스스로 종합해야 했다. 진행률(규칙 15)이 «목적지까지 남은 거리»를 보여주듯, 스토리지는 **«작업을 계속할 수 있는 여지»**를 보여줘야 한다. 특히 로컬 모델·빌드 캐시·시뮬레이터를 다루는 프로젝트에서는 수십 GB가 한 턴에 오간다.

    **① 매 턴 3요소 (진행률·대기표·성숙도와 같은 취급)**
    - **게이지**: 전체 대비 사용/여유를 막대로. 예: `▓▓▓▓▓▓▓░░░ 87GB 여유 / 926GB (91% 사용)`
    - **주요 소비처 표**: 상위 5~7개를 크기순 + **이번 턴 증감**(±GB). 무엇이 먹고 있는지 한눈에.
    - **판정 한 줄**: 🟢여유 / 🟡주의 / 🔴위험 + **지금 계획된 작업이 들어갈 수 있는지**(예: "받을 12.6GB는 들어감").

    **② 임계 기준** — 🟢 여유 ≥100GB 또는 ≥20% / 🟡 50~100GB 또는 10~20% / 🔴 <50GB 또는 <10%. 🟡부터는 **정리 후보를 함께 제시**하고, 🔴이면 **새 다운로드 착수 전 오너 승인**을 받는다.

    **③ 증감을 반드시 적는다** — 절대량보다 **변화**가 판단 재료다. «어제 148GB → 오늘 87GB»면 하루에 61GB를 쓴 것이고, 이 속도면 언제 바닥나는지가 보인다. 큰 증감에는 **원인**을 한 줄로(예: "모델 3종 수령 +52GB").

    **④ 회수 가능성을 구분해 표기** (전역 «디스크·대용량 다운로드 정책»과 한 쌍) — 정리 후보를 낼 때 🟢무비용(재생성·재빌드로 복구)과 🔴유비용(재다운로드 발생)을 반드시 구분한다. 🔴는 **해제 용량과 재다운로드 용량을 함께** 적어 오너가 저울질하게 한다.

    **⑤ 누적보고서에도** — 규칙 18과 같은 취급: 라운드에 그 턴 시점의 스토리지 스냅샷을 함께 싣는다. 시간에 따른 증감 추이가 곧 «이 프로젝트가 디스크를 얼마나 먹는가»의 기록이다.

    **⑥ 실측만 쓴다** — `df -h` + `du -sh` 실측값만 보고한다. 추정·기억으로 쓰지 않는다(전역 «다운로드 직전 실용량 재확인» 원칙과 동일 계열 — 용량은 인용하는 순간 틀린다).

### 위반 시
- 보고가 채팅에 흩어져 진행·타임라인 파악 비용↑. **과거 보고 누락 시 프로젝트 전체 맥락 유실**. 타임스탬프·기록물·복구점검 누락 시 추적성·복원력 약화. **캡쳐가 1열 나열·설명 없음이면 사용자 이해 비용↑ (규칙 7 위반)**. **요약 결의에 원문 딥링크가 없으면 오너가 세부를 찾을 수 없어 회신 자체가 불가 — 보고가 '읽었다' 수준에서 멈춤 (규칙 8 위반)**. **분과 보유 프로젝트가 divisions 탭·최신화를 누락하면 오너의 분과 소통 창구 상실 (규칙 9 위반)**. **진입 화면이 과거형 아카이브면 오너가 "지금 뭘 정해야 하나"를 스스로 종합해야 해 판단 비용이 폭증하고, 용어·요약 없이 쌓기만 하면 "너만 알아볼 수 있는 자료"가 된다 (규칙 10 위반 — P50 실사례)**. **글자만 있는 라운드는 오너가 다시 봐도 그 턴을 기억하지 못해 보고 자체가 무효가 된다 (규칙 11 위반 — P50 실사례)**. **회신 페이지가 클릭으로 열리지 않으면 오너가 경로를 들고 찾아가야 하고, 쓴 답이 저장되지 않으면 30분 들여 쓴 회신이 창을 닫는 순간 사라진다 — 회신 자체를 단념하게 만든다 (규칙 14 위반 — P53 실사례)**. **진행률·대기작업·성숙도가 채팅에만 남으면 압축과 함께 사라져, 몇 턴 뒤 그 라운드를 열어도 «그때 무엇이 막혀 있었나»를 알 수 없다 — 보고서가 추적의 정본 역할을 못 하고 오너는 이미 계획에 있던 것을 새로 지시하게 된다 (규칙 18 위반 — P42 실사례)**.

## 산출물 보존 + 개선 평가 의무 (Build Output Preservation & Comparison Rule)

> **추가 일자**: 2026-04-17 (P21 FEP에서 누적된 "이전 빌드 덮어쓰여 개선 평가 불가" 문제로 격상)

### 규칙 1: 산출물 파일명에 타임스탬프 필수
**반복 빌드/생성 가능한 산출물(영상, 이미지, 보고서, 모델, 빌드 아티팩트 등)은 반드시 타임스탬프 접두사를 포함한다.**
- 형식: `YYYYMMDD_HHMMSS_{설명}.{확장자}`
- 적용 대상:
  - 영상 빌드 (`output/20260417_014924_EP01_v3_lp_bubble.mp4`)
  - 이미지/일러스트 (`v3_layers/...`)
  - 분석 보고서, 측정 결과 JSON
  - 모델 체크포인트, 데이터셋 스냅샷
  - 컴파일된 바이너리 (반복 가능한 것)
- **금지**: 같은 파일명으로 덮어쓰기 (`output.mp4`, `result.json` 등 고정명)
- **예외**: 임시 작업 파일(`/tmp/*`), 캐시(`__pycache__`), 의존성 잠금(`package-lock.json`)

### 규칙 2: 개선 작업 후 비교 평가 의무
**"개선됨" 또는 "고침"이라고 보고하기 전에 반드시 다음을 수행:**

1. **이전 산출물 보존 확인**: 이전 버전이 같은 디렉토리에 보존되어 있는지 확인. 없으면 즉시 사용자에게 보고하고 작업 중단.
2. **정량 비교 측정**: 사용 가능한 객관적 지표로 이전 vs 현재 측정값 표 작성
   - 영상: 길이, 크기, 씬 수, 자막 수, 측정 가능한 품질 지표
   - 코드: 테스트 통과율, 성능 벤치마크, LOC, 복잡도
   - 데이터: 샘플 수, 정확도, 손실값
3. **시각/청각 검증** (해당 시): 같은 위치(타임스탬프/좌표)에서 이전 vs 현재 샘플 추출
4. **회귀 항목 명시**: 개선 항목 + **퇴보/유지 항목**도 빠짐없이 보고

### 규칙 3: "개선됨" 선언 유예
- AI(Claude)는 오디오 청취 불가, 영상 재생 관찰 불가, 사용자 체감 추정 불가
- 따라서 정량 지표가 좋아져도 **"개선됨"이라 단정하지 말고 "개선 시도"로만 표기**
- 사용자 시각/청각 검증 통과 후에만 "개선 확인" 으로 격상
- **위반 시 즉시 정정**: 같은 메시지 안에서 "개선됨 → 개선 시도" 로 표현 변경

### 규칙 4: 실패 패턴 추적
**같은 카테고리의 비교 평가 실패가 2회 발생하면**:
- 즉시 해당 프로젝트의 TRAP 시스템에 등록 + 전역지침 갱신
- 자동화 스크립트로 격상 (예: 빌드 후 자동 비교 보고서 생성)

1. **추가는 자유, 삭제는 허가제**: 새로운 콘텐츠 추가는 자유롭게 가능하나, 기존 콘텐츠의 삭제·축약·생략은 사용자의 명시적 요청이 있을 때만 허용

3. **의심스러우면 유지**: 특정 콘텐츠의 포함 여부가 불확실하면 포함하는 쪽을 선택

장시간 세션의 토큰 과소비를 방지하고, 새 세션에서 이전 작업의 핵심 맥락을 정확히 이어받기 위한 시스템.

2. **완전 일치**: 해당 P번호 사용
3. **하위 경로** (등록 프로젝트의 서브폴더이지만 그 자체는 미등록): 사용자에게 선택지 제시하고 답변 대기

   - (b) 상위 {P번호}의 임시 작업공간으로 진행

4. **부모 `.claude/CLAUDE.md`의 자동 로드는 범위 표식일 뿐 소속 확정이 아님** — CWD가 레지스트리 경로와 정확 일치할 때만 그 프로젝트 세션으로 간주

**채팅번호 할당 안전망 (타임스탬프 재확인)**: 새 채팅 개시 시 registry를 한 번 더 재read하여 max가 변했는지 확인. 변했으면 더 큰 값 사용. 동시 개시 채팅 간 경쟁 조건 최소화.

### 세션 번호 체계 (4계층, 2026-04-15 시행)

**형식**: `P{프로젝트}.{채팅}.{포크}.{Agent}` — `wc` 등 정책 태그는 폐지

| 계층 | 의미 | 증가 시점 |
|------|------|-----------|
| 프로젝트 N | 프로젝트 번호 | 신규 프로젝트 생성 (전역) |
| 채팅 C | 채팅창 식별 | 새 채팅창 개시 (registry SSOT) |
| 포크 F | 자동포크 식별 | 같은 채팅 내 압축·자동포크 (채팅 내) |
| Agent A | Agent 파견 식별 | `.0`=원본 스레드, `.1+`=Agent (포크 내) |

**증가 규칙**:
- **새 채팅 개시**: `registry.md` max 채팅번호 +1 → `P{N}.{max+1}.1.0`
- **같은 채팅 내 자동포크**(압축 등): 채팅 고정, 포크 +1, Agent=0 리셋
  - 예: `P3.28.1.0` → 압축 → `P3.28.2.0`
- **Agent 파견**: 채팅·포크 고정, Agent +1
  - 예: `P3.28.1.0` → 파견 → `P3.28.1.1`, 또 파견 → `P3.28.1.2`
- **Agent 내부에서 또 Agent 파견**: 계층 증가 금지, Agent번호만 +1 (`.1.1.1.1` 꼬리 방지)
- **타 프로젝트 Agent 파견**: 대상 프로젝트 registry에서 새 채팅번호 할당
  - 예: `PM.17.1.0`이 P3에 파견 → P3 registry max=28 → `P3.29.1.0` 생성
- **교차채팅 포크**(채팅 오류로 재개설): 새 채팅번호 할당, 족보는 **`포크원` 필드로만 추적**
  - 예: `P1.3.5.0` 오류 → 새 채팅 `P1.4.1.0` (포크원: `P1.3.5.0`)
  - **계층을 끌어올리지 않는다** (루트번호만으로 포크체인을 추적하지 않음)

**유산 세션 호환**: 2026-04-14 이전 평면 번호(`P3.28wc` 등)는 그대로 보존. 해당 세션에서 신규 포크 발생 시부터 4계층 적용 (유산 번호는 묵시적 `.1.0`으로 간주: `P3.28wc` → 압축 → `P3.28.2.0`).

### 측정 단위 = "우리 세션"의 실제 처리량 (P39에서 도출, 2026-06-06)
> 사용자 지시: 인간 팀 기준 개발시간은 무의미. **실제 세션의 대화 왕복 + 그 결과 산출된 코드/문서의 산출 시간**으로 추정·소통하라. "너와 나의 대화·산출물 산출시간이 실제 작업시간 예측에 유효."
- **단위**: "유사 작업을 우리가 (이번/지난) 세션에서 ~대화라운드 / ~분에 산출했다"는 *실측 처리량*. 일정 = 설계대화 라운드 수 + 산출물 개수 × 우리의 실측 산출속도.
- **데이터 부족 시**: 과거 유사 작업에서 추정(예: P36 기능 1건당 ~30분, 한 오후 8커밋+배포; 본 세션처럼 전략문서 1건당 수 분).
- **표기**: "설계대화 N라운드 + 산출물 M개 → 세션 약 K시간/세션수"처럼 *우리 처리량*으로. 인간-개월/인간-팀 환산 금지.
- **누적**: 세션마다 실측을 모아 추정 정확도↑(필요시 프로젝트 registry/메모리에 처리량 기록).

## 지시 누락 방지 — 작업 추적 의무 (Task Tracking Mandate)

> **추가 일자**: 2026-07-23 (P50 오너 지시). 계기: 한 세션에서 지시 2건(아트 재생성 착수·기기 설치)이
> **오너가 지적하고서야** 발견됨. 오너 원문: *"내가 지시한 작업들 잊어버리고 멈춰있는 것들이 종종
> 발생하는데 내가 누락작업 확인하라고 하면 점검좀 해줘. **스스로도 주기적으로 누락작업을 점검해야지
> 내가 지시하지 않더라도.** 멀티에이전트로 돌리면 될텐데 왜 일을 누락시키는 거야. … **일이 바빠서
> 내가 동시에 지시하는 사항들이 많아서 누락되는 작업이 계속 발생할거야.**"*

**원인 진단**: 사용자가 한 메시지에 여러 지시를 담거나 턴 중간에 새 지시를 추가할 때, 어시스턴트가
**추적 장치 없이 기억에 의존**하면 앞 지시를 처리하는 사이 뒤 지시가 소실된다. 특히 ①긴 백그라운드
작업 대기 중 ②턴 중간 삽입 메시지 ③여러 갈래로 분기된 작업에서 빈번하다.

### 규칙 (필수)

1. **새 지시 수신 즉시 등록** — 사용자 메시지에 **작업이 2건 이상**이거나, 턴 중간에 새 지시가
   삽입되면 **먼저 `TaskCreate`로 전부 등록**한 뒤 실행에 들어간다. 등록을 미루고 "기억해서
   하겠다"는 금지. 즉시 처리되는 1건짜리 사소한 요청은 예외.
2. **착수·완료 표시** — 작업 시작 시 `in_progress`, 실제로 끝났을 때만 `completed`.
   부분 완료·검증 실패는 완료로 표시하지 않는다.
3. **턴 종료 전 자가 점검 (의무)** — 응답을 마치기 전 `TaskList`로 미완 작업을 확인하고,
   **남은 것이 있으면 응답에 명시**한다("남은 작업: N건 — …"). 사용자가 묻지 않아도 한다.
4. **"누락 확인" 요청 시 전수 점검** — 사용자가 누락을 물으면 TaskList + 대화 전문을 대조해
   **등록되지 않은 지시까지** 찾아 보고한다(등록 자체를 빠뜨렸을 수 있다).
5. **장시간 대기 중 재확인** — 백그라운드 작업(빌드·생성·워크플로)을 기다리는 동안
   **다른 미완 작업을 먼저 처리**한다. 대기가 곧 유휴가 되어선 안 된다.
6. **완료 보고의 정직성** — "했다"고 보고하기 전에 **실제 산출물을 확인**한다.
   코드 수정 = 배포 아님, 빌드 = 설치 아님, 생성 시작 = 완료 아님. 이 구분을 흐리지 않는다.

7. **★긴 메시지는 문단 단위로 쪼개 등록한다 (2026-07-27 P50 실사례로 추가)** —
   누락은 "지시를 못 봤을 때"가 아니라 **한 메시지 안에 지시가 여러 개일 때** 발생한다.
   실측: 오너의 한 메시지에 ①관리자 기능 ②갤러리 선택 ③대사 추가·제거 ④경량추론모델 도입 검토
   ⑤말투 교육내용 수정 — **5건**이 들어 있었는데, 앞 3건만 처리하고 뒤 2건은 등록조차 안 됐다.
   ⇒ **메시지가 3문단 이상이거나 "그리고/또한/마찬가지로"로 이어지면, 문단마다 지시가 있다고
   가정하고 문단 단위로 훑어 전부 등록한다.** 특히 **메시지 뒷부분**이 위험하다
   (앞부분을 처리하는 동안 뒤가 컨텍스트에서 밀려난다).
8. **★"검토해줘/보고해줘"도 작업이다** — 코드를 고치는 것만 작업이 아니다.
   조사·검토·타당성 판단 요청은 **산출물(보고)이 나올 때까지 미완**이며, 등록 대상이다.
   위 실사례에서 누락된 2건이 전부 "검토해서 보고해줘" 유형이었다.
9. **★주기적 전수 대조 (사용자가 묻기 전에)** — 세션이 길어지면 압축으로 초반 지시가 사라진다.

10. **★내부 작업목록은 사라진다 — 보고서 원장을 정본으로 둔다 (2026-07-27 P51 실사례로 추가)**:

    ⇒ ⓐ TaskUpdate/TaskList가 예상과 다르게 응답하면 **즉시 전수 재등록** ⓑ 진짜 정본은

2. **턴 종료 전 점검 (체크포인트)**: 의미 있는 산출물을 만든 턴은 응답을 마치기 전에 "기록물 5종(세션·프로젝트 CLAUDE.md·TRAP·메모리·registry) 중 갱신 필요한 것"을 빠르게 자가 점검 → 누락 발견 시 그 턴 안에서 보강한다.
3. **병렬 처리 (주 작업 중단 금지)**: 기록 점검·갱신은 주 작업을 멈추지 않고 병렬로 수행한다(사용자 피드백: 기록 위해 작업 흐름을 멈추지 말 것).
4. **결과**: 압축이 언제 발생하든 직전 맥락이 파일에 보존되어 무손실 복원 가능.

- **연계**: 저장 자원의 위치·용도는 reference 메모리 또는 프로젝트 `.claude/CLAUDE.md`에 기록(압축 후에도 위치 추적 가능). 위 "압축 전 선제적 기록물 점검"과 한 쌍.

### 지침 변경 자동 감지 + 행동규칙 기계 가드 (Instruction Hooks)

> 도입: 2026-06-11 (P38 세션, 사용자 지시: "왜 자동으로 전역지침 내용 후크 안됐는지 검토해서 보완"). 원인: 지침은 **세션 시작 시 1회 스냅숏 로드**라 세션 도중 타 세션의 갱신이 자동 반영되지 않고, 행동 규칙(Safari 등)에 기계 강제 장치가 없었음.

**전역 hooks(`~/.claude/settings.json`)가 자동 수행한다:**
- **UserPromptSubmit** `~/.claude/hooks/claude_md_watch.py`: 매 사용자 메시지 제출 시 전역지침 + cwd→$HOME walk-up 경로의 모든 `.claude/CLAUDE.md` 변경(타 세션 갱신 포함)을 mtime/sha로 감지 → "재Read하라" + 변경 섹션 요약을 컨텍스트에 주입. **알림 수신 시 해당 파일을 Read로 다시 읽고 새 규칙 적용 의무.** (상태: `~/.claude/.cache/md_watch/{세션ID}.json`, 30일 자동 정리)
- **PreToolUse(Bash)** `~/.claude/hooks/safari_guard.py`: `.html` 대상 `open` 명령에 `-a Safari`가 없으면 deny + 사유 반환 (HTML 산출물 Safari 규칙의 기계 이행).
- **SessionStart** `~/.claude/hooks/session_start.sh`: 레지스트리 SSOT·4계층 번호에 더해 **자주 위반되는 행동규칙**(Safari·P{N} 표기·누적 보고서 섹션 재확인·검수 페이지·압축 포크 +1)을 주입 — 압축 후 재시작 시에도 발화하므로 규칙 유실 방지.
- 새 "자주 위반 규칙"이 생기면: ① session_start.sh에 1줄 추가 ② 기계 차단 가능하면 PreToolUse 가드 스크립트 추가.

### ⚠️ 전역지침 동시편집 충돌 방지 프로토콜 (2026-07-28 추가)

> **오너 지시**: *"현재 P43에서도 전역지침 조치중이니까 전역지침 수정으로 인한 **충돌 발생하지 않도록 주의**해줘. **충돌방지관련 조치가 별도로 필요하다면 이에관한 사항도 전역지침에 반영**해줘야겠다."*

**문제**: `~/.claude/CLAUDE.md`는 **전 프로젝트가 공유하는 단일 파일**인데, 여러 세션이 동시에 진행된다. 나중에 저장한 세션이 상대의 변경을 **소리 없이 덮어쓰면**, 방금 다른 프로젝트가 격상한 규칙이 통째로 사라진다. UserPromptSubmit 훅(`claude_md_watch.py`)이 "타 세션이 지침을 바꿨다"고 알리는 상황은 이미 일상적으로 발생한다.

**전역지침·공유 기록물(전역 엔진 `~/.claude/scripts/*`, `~/.claude/instructions/*` 포함)을 수정할 때 아래를 지킨다.**

1. **★전면 재작성(Write) 금지 — 앵커 기반 최소 Edit만.** 파일 전체를 다시 쓰면 그 순간 다른 세션의 변경이 전부 사라진다. 반드시 **고유 문자열 앵커**를 잡아 `Edit`으로 국소 삽입·치환한다. 앵커는 **바꾸려는 지점의 직전·직후 문장**을 포함해 유일성을 확보한다(같은 문구가 문서에 여러 번 나오는지 먼저 `grep -c`로 확인).
2. **★편집 직전에 반드시 재Read.** 세션 시작 시 로드된 스냅샷을 신뢰하지 않는다(그 사이 다른 세션이 고쳤을 수 있다). 훅 알림을 받았다면 **무조건** 다시 읽는다. 편집 전 `크기·줄수·mtime·sha` 를 기록해 둔다.
3. **★편집 직후 즉시 재Read로 "공존" 확인.** 자기 문장이 들어갔는지만 보고 끝내면 안 된다. **① 내 변경이 있고 ② 타 세션의 최신 변경도 그대로 남아 있는지**를 함께 확인한다(편집 전후 줄수·섹션 목록 비교, 최근 다른 프로젝트가 추가한 섹션 제목 존재 확인).
4. **★섹션 신설은 append 지향.** 새 규칙은 **기존 섹션 끝 또는 파일 말미**에 붙인다. **기존 번호를 재배열하지 않는다** — 두 세션이 동시에 번호를 밀면 번호가 충돌하고 상호 참조가 깨진다. 새 번호가 겹칠 것 같으면 번호 대신 소제목으로 단다.
5. **★같은 규칙을 동시에 건드렸으면 덮어쓰지 말고 병합.** 나중 세션은 상대 문장을 지우지 말고 **양쪽 취지를 합친 뒤**, 그 섹션에 `(YYYY-MM-DD P{N}·P{M} 병합)`을 남긴다.
6. **대규모 개편은 보류.** 다른 세션이 지침을 만지는 중이라는 신호(훅 알림·오너 언급)가 있으면, 재구성·번호 정리·섹션 이동 같은 **광범위 편집은 미루고** 오너에게 알린다. 급하지 않은 정리는 언제든 다음에 할 수 있다.
7. **여러 곳을 고칠 땐 한 번에 하나씩.** 한 Edit 후 검증하고 다음 Edit으로 간다. 실패한 Edit을 같은 내용으로 재시도하지 말고, **재Read → 앵커 재확보** 후 진행한다(앵커가 안 맞는다는 것은 파일이 이미 바뀌었다는 뜻이다).
8. **보고 의무**: 전역지침을 고쳤으면 **무엇을 어디에 추가했는지**(섹션명·규칙번호)를 그 턴 보고에 명시한다. 다른 프로젝트 세션이 같은 파일을 읽을 때 충돌 여부를 판단할 수 있어야 한다.

**위반 시**: 다른 프로젝트가 방금 격상한 규칙이 흔적 없이 사라진다. 그 프로젝트는 규칙이 사라진 줄도 모른 채 예전 방식으로 일하게 되고, 오너는 같은 지시를 두 번 내려야 한다 — 지침 체계 자체의 신뢰가 무너진다.

### 대화 전문 자동 MD 미러 (Transcript MD Mirror)

> 도입: 2026-06-11 (P41 세션, 사용자 지시: "압축으로 컨텍스트가 유실되지 않도록 주기적으로 모든 대화를 MD로 저장, 전 세션 전파")

**전역 hooks가 자동 수행한다 (Claude의 별도 저장 작업 불필요):** `~/.claude/settings.json`의 **Stop(매 턴 종료, async) · PreCompact(압축 직전) · SessionEnd** 훅이 `~/.claude/scripts/transcript_to_md.py`를 실행해 현재 세션 transcript JSONL을 읽기 좋은 MD로 변환 저장한다.

- **저장 위치 (2중 미러)**:
  1. `{프로젝트}/memory/sessions/transcripts/{세션UUID}.md` — cwd에 `.claude/` 또는 `memory/`가 있을 때 (iCloud 동기화로 타 맥 복구 가능)
  2. `~/.claude/transcripts_md/{프로젝트슬러그}/{세션UUID}.md` — 항상 (중앙 미러, cron 백업 대상)
- **내용**: 사용자·Claude 발화 전문 + 도구 호출 1줄 요약(🔧) + 도구 결과 300자 미리보기(↩️) + 압축 요약(📦). 서브에이전트 사이드체인 제외. 매 실행마다 전체 덮어쓰기(원본은 JSONL이 보존).
- **Claude 의무**:
  1. **압축 복원·세션 재개 시** 세션지침과 함께 이 미러 MD를 참조해 유실 맥락(특히 사용자 원문 발화)을 복원
  2. 훅 미작동 의심 시 수동 실행: `echo '{"transcript_path":"<JSONL경로>","cwd":"<프로젝트>"}' | python3 ~/.claude/scripts/transcript_to_md.py`
  3. 이 미러는 기록물 5종(세션지침·프로젝트 CLAUDE.md·TRAP·메모리·registry)을 **대체하지 않는다** — 원시 대화 보존층일 뿐, 구조화 기록은 기존 규칙대로 유지
- **전파**: user-level 설정이므로 모든 신규 세션에 자동 적용. 이미 실행 중인 다른 세션은 재시작 후 적용.

### 압축 감지 시 대응

자동 컨텍스트 압축이 발생하면:
1. 사용자에게 "⚠️ 압축 발생" 알림
2. 세션지침 즉시 갱신 + **포크번호 +1 자동 부여** (`P{N}.{C}.{F+1}.0`) — ⚠️ **채팅번호 건드리지 말 것** (타 채팅 충돌 방지 핵심)
3. **`## 금지/확정 사항` 섹션을 가장 먼저 확인** — 이전 세션 금지/불가 사항 필수 전달
4. **사용자에게 새 채팅을 열라고 안내하지 않는다** — 사용자는 같은 채팅에서 계속 작업
5. 유실 의심 맥락은 **대화 전문 미러** `memory/sessions/transcripts/{세션UUID}.md`에서 원문 복원

### 1. 정리 제안은 반드시 「재다운로드 유발 여부」로 분류한다
| | 뜻 | 예 |
|---|---|---|
| 🟢 **무비용** | 삭제해도 네트워크 0 — 재생성·재빌드·USB 재복사로 복구 | 시뮬레이터 **기기**, Xcode `DerivedData`, `iOS DeviceSupport`, 빌드 산출물 |
| 🔴 **유비용** | 삭제 시 **재다운로드 발생** | 시뮬레이터 **런타임**, brew·npm·pip·gradle 캐시, `~/.cache`(huggingface), ollama 모델, Unity 에디터 |

- 🔴 항목은 **"해제 용량 N GB / 재다운로드 M GB"를 함께** 적어 오너가 저울질할 수 있게 한다.
- **내용을 확인하지 않고 "대체로 안전"이라 말하지 않는다.** (P51 실사례: `~/.cache`를 안전으로 분류했는데
  실제로는 huggingface 모델 가중치 2.1GB였다 — 재다운로드 폭탄.)

### 2. 시뮬레이터 최소 보유
- **테스트마다 새 기기를 만들지 않는다.** 기존 기기를 재사용한다. 목록은 실제 검증에 쓰는
  최소 세트(예: iPhone 1대 + iPad 1~2대)만 유지.
- **기기 ≠ 런타임**: `xcrun simctl delete`는 **기기 데이터만** 지운다. OS 런타임은
  `/Library/Developer/CoreSimulator/Volumes/`에 남으므로 **기기 재생성은 오프라인·즉시·무료**다.
  → 기기 정리는 🟢 무비용이니 망설이지 말 것.
- **새 런타임(iOS/watchOS/tvOS/visionOS) 설치는 오너 승인 필수** — 런타임은 **7~16GB 다운로드**다.
  프로젝트가 대상으로 하지 않는 플랫폼의 런타임은 애초에 받지 않는다.

### 3. 대용량 다운로드는 착수 전 고지·승인

- **디스크 실점유는 다운로드 용량보다 크다**(압축 해제·중간 산출물). 실측 후 차이를 정직하게 보고한다.
  (P51: "11GB 다운로드" 고지 → 실제 디스크 23GB.)
- 오너가 Wi-Fi 환경일 때로 미룰 수 있으면 미룬다.

> 수 있도록 **분초단위뿐만 아니라 동시에 찍힌 캡쳐들도 전후관계가 파악**되도록 접두어로 달고,

**⓪ 진단**: 그동안 캡쳐는 **대화 안에만** 있었다. 대화가 압축되면 통째로 사라져, 매뉴얼·누적보고서에
쓰려 해도 **다시 찍는 수밖에** 없었다(P43 실사례: 하루치 작업 캡쳐 전량 복구 불가). 캡쳐 1장은
토큰이 비싸고 재현도 어려우므로 **찍는 즉시 디스크에 남기는 것이 정답**이다.

### 1. 자동 저장 — 이미 걸려 있다 (손댈 것 없음)
전역 훅 `~/.claude/hooks/capture_saver.py` (`settings.json` **PostToolUse**)가 화면 캡쳐 계열 도구
(브라우저 `computer`/`browser_batch`, 데스크탑 `computer-use`, iOS 시뮬레이터, `zoom`, `gif_creator`)의
응답에서 **그 이미지 자체**를 꺼내 디스크에 쓴다. 어시스턴트가 따로 저장 명령을 내릴 필요가 없다.
- **user-level 설정이므로 신규·기존 프로젝트 전부에 자동 적용**된다(세션 재시작조차 불필요 — P43 실측).
- 저장 위치: `{프로젝트루트}/docs/captures/{YYYY-MM-DD}/` (루트를 못 찾으면 `~/.claude/captures/_unassigned/`).
- 같은 폴더 `_index.tsv`에 `파일·시각·도구·동작·화면(자동추정)·설명` 한 줄씩 누적.

### 2. 파일명 규칙 — 「완전 시간순」 + 「이름만 봐도 내용」
```
20260813-214724.432_00001_게시판_T10검색5건_제목클릭했으나_미반응.jpg
└─날짜─┘└─시각─┘└ms┘ └일련┘ └──────────── 무엇을 찍었나 ────────────┘
```
- **밀리초까지** → 같은 초에 여러 장을 찍어도 순서가 남는다.
- **전역 일련번호**(`~/.claude/.cache/capture_seq`, 파일잠금 증가) → 밀리초까지 같아도 전후가 확정된다.
  한 번의 배치가 여러 장을 돌려주면 `-1 -2` 꼬리가 더 붙는다.
- **사전식 정렬 = 작업 순서** — 파인더에서 이름순으로 두면 그대로 작업 타임라인이다.
- 뒤쪽 설명은 훅이 자동 추정한 값(탭 제목·동작). **그대로 두지 말 것 — 아래 3.**

### 3. 어시스턴트 의무 — 캡쳐에 「사람 말」 이름 달기

```bash
python3 ~/.claude/scripts/capture_label.py "무엇을 찍었나"          # 최근 1장
python3 ~/.claude/scripts/capture_label.py "검색 입력" "결과 5건" "클릭 후"   # 최근 3장 (오래된→최신)
python3 ~/.claude/scripts/capture_label.py --list                  # 설명 없는 것 확인
```
- 이름은 **나중에 매뉴얼·보고서에서 검색할 말**로 짓는다: `무엇의_무슨상태_결과`

## 🤝 크로스 어시스턴트 협업(이관) 프로토콜 — 그록↔클로드 등 (2026-08-19, P60·P64에서 도출)

> 계기: 그록(Grok CLI) 토큰 소진으로 P60 FlowDash를 클로드가 이어받음. 그록이 설계한 이관 패키지(전역 G013,
> P64 HJGF 선례)가 실측으로 유효했으므로 클로드 쪽 표준으로도 격상한다. 오너: *"이러한 협업은 앞으로 다른
> 프로젝트들에서도 자주 발생할 예정."* **타 어시스턴트(그록·Gemini 등)와 프로젝트를 주고받을 때 이 절을 따른다.**

### 1. 번호와 원장 — 프로젝트는 하나다
- **P번호 유지 + 세션 포크.** 이관받았다고 새 P번호를 따지 않는다 (같은 프로젝트가 두 원장으로 갈라지면 합칠 때 사고).
  예: 그록 `P60.1.2.0` → 클로드 `P60.2.1.0` (새 채팅 계층, 포크원 = 상대 세션).
- **공유 원장은 `~/.claude/registries/P{N}.md` 한 파일뿐** — 양쪽 다 읽고, **행 추가·자기 칸 기입만** 한다.
  각자 레지스트리를 따로 만들지 않는다.
- 상대의 전역지침(`~/.grok/rules/` 등)은 **읽기 전용**. 내 전역지침도 상대가 쓰지 않는다.

### 2. 폴더 — 정본 공유 편집 금지, 시각 사본으로만
- 보내는 쪽 정본은 **잠금**(`HANDOFF_LOCK.md`) — 받는 쪽은 정본·그 심볼릭 링크를 열지도 않는다.
- 받는 쪽은 **시각 사본**(`{프로젝트}_P{N}.{C}_{수신자}_{YYYYMMDD_HHMMSS}/`)에서만 작업한다.
  오너가 별도 작업 루트를 지정하면 거기서 작업하되, **원 사본 폴더에 이동 경로 스텁을 남긴다** (상대가 추적 가능하게).
- 받는 즉시 **수령 기준점 git 커밋**을 만든다 — 이후 diff가 곧 내 변경 전량이며 반환 패키지의 원료다.

### 3. 이관·반환 패키지 (시각 스냅샷, 덮어쓰기 금지)
- 이관: `YYYYMMDD_HHMMSS_{수신자}이관/` — ①먼저 읽어주세요(충돌 방지 한 장) ②번호·폴더 ③원장 공유 범위
  ④기록물 위치 ⑤원격 쓰기 잠금 ⑥지금 상태·다음 작업 ⑦되돌릴 때 + `records/` 핵심 기록물 스냅샷.
- 반환: `YYYYMMDD_HHMMSS_{송신자}반환/` — 무엇을 했나 · 바뀐 파일 목록(기준점 diff) · 대화록 전문 ·
  배포했다면 버전 ID · 늘어난 REQ/TRAP 사본. **보낸 쪽은 반환 패키지와 이관 패키지를 대조한 뒤에만 정본에 반영.**
- 절대 금지: 키·시드·`.env`·인증 토큰·`node_modules`를 패키지에 넣는 것.

### 4. ★기록물 경계 마커 — 나중에 되이관돼도 누가 쓴 것인지 헷갈리지 않게
- 상대가 만든 **공유 문서에 추기**할 때는 반드시 경계를 표시한다:
  `<!-- CLAUDE:P{N}.{C}.{F}.{A} BEGIN (날짜) -->` … `<!-- CLAUDE:... END -->` (코드 파일은 주석 문법으로 동일하게).
- 마커 밖은 **한 글자도 고치지 않는다** (append 지향 · 삭제/재배열 금지 — «전역지침 동시편집 충돌 방지»와 동일 취지).
  표(원장)는 마커 대신 **행의 세션번호 컬럼**이 경계 역할을 한다.
- 새로 만든 파일은 머리에 마커 한 쌍(또는 «이 파일 전체가 클로드 작성») — 파일 단위 귀속을 명시.

### 5. 원격 자원 — 폴더는 복사돼도 라이브는 하나다
- 배포(워커·서버)·git push·공유 KV/DB는 **한 시점에 한쪽만** 쓴다. 이관 문서에 라이브 버전 ID를 명기하고,
  보낸 쪽은 재개 전까지 배포·푸시하지 않는다.

### 6. 수신 직후 의무 (받는 쪽 체크리스트)
① 이관 패키지 전 문서 정독 → ② 공유 원장에 UUID 등 자기 칸 기입 → ③ 기준점 커밋 →
④ **상대 작업 전반 감사**(잘된 점/부족한 점 — 기록물 대조 방식, 부족한 점은 보완 계획과 함께 보고서에) →
⑤ 준수 보고를 **상대 폴더에** 남김(내가 지침을 어떻게 따랐는지 + 이행 표) → ⑥ 누적보고서에 이관 라운드 기록.

### 위반 시
정본이 소리 없이 갈라지고(두 AI가 같은 파일을 다른 내용으로), 기록물의 저자 경계가 사라져 되이관 시
서로의 기록을 덮어쓴다. 원격 자원 동시 쓰기는 라이브를 마지막 배포자가 덮는 사고가 된다.
